# SOP Drift Detector

MyClick Backend · Click.uz

Скрипт, который автоматически находит расхождение между задокументированными процессами (Confluence) и реальными изменениями в коде (Jira + GitLab). Раз в неделю анализирует закрытые задачи, смерженные MR и связанную документацию, и генерирует HTML-отчёт со страницами, которые нужно обновить.

## Проблема

Команда хранит документацию в Confluence (space `Products`), задачи ведёт в Jira (`MYCLICK`), код — в GitLab. После того как инженер закрывает задачу и мержит MR, связанные страницы Confluence часто остаются устаревшими — никто не обновляет документацию вручную. Со временем это приводит к тому, что:

- новые члены команды работают по устаревшим инструкциям;
- AI-агенты и автоматизации используют неактуальные данные;
- рассинхронизация между кодом и документацией накапливается месяцами.

## Как это работает

Скрипт последовательно проходит 5 этапов (`src/index.ts`):

1. **Jira** (`src/clients/jira.client.ts`) — получает задачи одного или нескольких проектов `jira.projectKey` (из `config.json`) со статусом `Test`, обновлённые за последние `daysBack` дней, и оставляет только те, чей заголовок начинается хотя бы с одного из `jira.titlePrefix` (по умолчанию `[Back]` — только backend-задачи). GitLab и Confluence при этом общие на все подключённые проекты — поиск MR идёт по ключу задачи независимо от проекта, дерево Confluence не привязано к конкретному Jira-проекту:
   ```
   GET /rest/api/2/search?jql=project=MYCLICK AND status=Test AND updated>=-7d
   ```
2. **GitLab** (`src/clients/gitlab.client.ts`) — один раз за прогон забирает **все** смерженные MR проекта за последние `gitlab.mrLookbackDays` дней (не то же самое, что `daysBack` — код обычно мержится заметно раньше, чем задача доходит до статуса `Test` в Jira, поэтому окно для MR шире по умолчанию), затем для каждой задачи локально ищет совпадающие MR по ключу задачи в заголовке, описании **или названии ветки** (регистронезависимо — покрывает и `feature/myclick-123-fix`, и заголовки без ключа вовсе). Для найденных MR забирает diff изменённых файлов (бинарные и lock-файлы отфильтровываются, diff каждого файла обрезается до 10 000 символов):
   ```
   GET /api/v4/projects/{id}/merge_requests?state=merged&merged_after=...
   GET /api/v4/projects/{id}/merge_requests/{iid}/diffs
   ```
3. **LLM-анализ** (`src/analyzers/diff.analyzer.ts`) — объединённый diff всех MR отправляется в Claude (`claude-haiku-4-5-20251001`), который возвращает JSON: краткое описание изменения в поведении системы, ключевые слова для поиска в документации и флаг `hasDocImpact`. Если LLM недоступен или диффов нет — используется fallback на ключевые слова из заголовка задачи и MR.
4. **Confluence** (`src/clients/confluence.client.ts`) — рекурсивно (до 5 уровней вложенности) собирает все дочерние страницы под `CONFLUENCE_ROOT_PAGE_ID`, вместе с датой последнего обновления и текстом страницы (`body.storage`, очищенным от HTML).
5. **Матчинг и отчёт** (`src/analyzers/semantic.matcher.ts`, `src/analyzers/matcher.ts`, `src/reporters/html.reporter.ts`) — заголовки и начало текста всех страниц Confluence вместе с описанием изменения отправляются в Claude (`SemanticMatcher`), который выбирает семантически связанные страницы (понимает синонимы и другую терминологию, а не только буквальные совпадения слов). Если LLM недоступен или вернул нераспознаваемый ответ — используется fallback на keyword-матчинг (`Matcher`): сопоставление ключевых слов с заголовком и содержимым страницы, с порогом релевантности (`MIN_SCORE = 3`), отсекающим случайные совпадения. В обоих случаях страница считается устаревшей (`isDrifted`), если она не обновлялась дольше 14 дней или обновлялась раньше, чем был смержен самый свежий MR задачи. Не больше 3 страниц на задачу попадают в HTML-отчёт.

```
sop-drift-detector/

│   │   ├── diff.analyzer.ts      # LLM-анализ diff'а
│   │   └── matcher.ts            # матчинг изменений → страниц Confluence

└── README.md
```

## Требования

- Node.js 20+
- Yarn (в репозитории закоммичен `yarn.lock`)
- Доступ и токены к Jira, GitLab, Confluence и Anthropic API

## Установка

```bash
git clone <repo>
cd sop-drift-detector
yarn install
cp .env.example .env
# заполнить .env реальными токенами
# отредактировать config.json под свой Jira/GitLab/Confluence (в репозитории он уже есть с тестовыми значениями)
```

## Конфигурация

Настройки разделены по чувствительности: секреты — в `.env` (не коммитится), всё остальное — в `config.json` (коммитится в git, поэтому изменения настроек видны в диффах/PR).

### Секреты (`.env`)

| Переменная            | Описание                                                          |
| ---------------------- | ------------------------------------------------------------------- |
| `JIRA_TOKEN`           | Personal Access Token (отправляется как `Authorization: Bearer`)   |
| `GITLAB_TOKEN`         | Private Token с доступом к проекту                                 |
| `CONFLUENCE_TOKEN`     | Personal Access Token (отправляется как `Authorization: Bearer`)   |
| `ANTHROPIC_API_KEY`    | Ключ Anthropic API для LLM-анализа                                 |

### Настройки (`config.json`)

| Поле                       | Описание                                                                 |
| --------------------------- | --------------------------------------------------------------------------- |
| `jira.url`                  | Базовый URL Jira (обязательно)                                            |
| `jira.projectKey`           | Строка или массив строк — ключ(и) проекта(ов), например `["MYCLICK", "OTHERPROJ"]` (опционально, по умолчанию `MYCLICK`) |
| `jira.titlePrefix`          | Строка или массив строк — обрабатывать только задачи, чей заголовок начинается с одного из этих префиксов, например `["[Back]", "[API]"]` (опционально, по умолчанию `[Back]`) |
| `gitlab.url`                | Базовый URL GitLab (обязательно)                                          |
| `gitlab.projectId`          | ID проекта в GitLab (обязательно)                                         |
| `gitlab.mrLookbackDays`     | За сколько дней назад искать смерженные MR (опционально, по умолчанию `60`) |
| `confluence.url`            | Базовый URL Confluence (обязательно)                                      |
| `confluence.rootPageId`     | ID корневой страницы, под которой ищутся дочерние (обязательно)           |
| `daysBack`                  | За сколько дней назад искать задачи (опционально, по умолчанию `7`)       |

## Формат отчёта

HTML-отчёт (`reports/report-YYYY-MM-DD.html`) содержит для каждой обработанной задачи:

- ключ и название задачи Jira;
- ссылку на MR в GitLab и дату мержа;
- LLM-описание того, что изменилось, и ключевые слова;
- список связанных страниц Confluence с датой последнего обновления;
- статус страницы: ⚠️ Устарела / ✅ Актуальна.

Пример записи:

```
MYCLICK-456 | Изменена логика авторизации через OTP
  MR: "feat: update otp validation flow" (merged 10 Sep 2026)
  LLM: "изменён алгоритм валидации OTP кода"
  ⚠️  "OTP авторизация" — обновлялась 3 месяца назад
  ⚠️  "Auth Flow" — обновлялась 5 месяцев назад
```

## Текущие ограничения

- Скрипт только читает данные — не обновляет документацию автоматически.
- Основной матчинг семантический (через LLM), но при сбое LLM используется keyword-fallback — в этом режиме возможны как пропуски, так и ложные срабатывания на общих словах.
- Если ключ задачи (например, `MYCLICK-123`) есть только в сообщениях коммитов внутри MR (не в заголовке, описании или названии ветки) — связь между задачей и MR не находится.
- LLM анализирует только текстовый diff, бинарные и lock-файлы игнорируются.
- Поддерживает несколько проектов Jira, но только один проект GitLab и одно дерево страниц Confluence на все из них (без мультитенантности).
